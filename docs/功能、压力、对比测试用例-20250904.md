## 2. 通用前置条件与判定

- 系统已部署并可登录，准备好费用报销、考勤、规章制度、合规制度等不同字数的 DOC/DOCX 文档。
- 记录请求发起时间、首 token/响应时间、思考时间、输出字数、每秒输出字数、整体完成时间和错误信息。
- 功能用例要求：结果正常返回、引用内容来自上传文档、无明显截断或答非所问。
- 压力用例要求：并发任务按场景完成；超时、失败任务必须可见且不影响其他任务；服务不崩溃。
- 对比用例要求：在相同输入下记录两模型指标，并比较正确性、完整性和耗时。

## 2.1 API 执行方式

AI 对话、长输出和并发场景可通过 OpenAI 兼容接口执行。接口地址以 `automation/config.json` 为准，单次请求模板如下：

```bash
curl -X POST 'http://127.0.0.1:1025/v1/chat/completions' \
  -H 'Content-Type: application/json' \
  -d '{
    "messages": [
      {"role": "system", "content": "you are a helpful assistant."},
      {"role": "user", "content": "帮我写一篇万字长文"}
    ],
    "max_tokens": 32,
    "stream": false,
    "do_sample": true,
    "repetition_penalty": 1.00,
    "temperature": 0.6,
    "top_p": 0.6,
    "top_k": 20,
    "model": "deepseek14b"
  }'
```

参数化执行时，替换以下字段：

| 参数 | 用例要求 |
|---|---|
| `messages[1].content` | 替换为具体测试提示、文档问答或长输出指令 |
| `max_tokens` | 32 用于连通性和截断验证；长文验收应按目标字数换算并单独记录 |
| `stream` | `false` 验证非流式完成；需要测首 token 和持续输出时改为 `true` |
| `model` | 功能测试使用 `deepseek14b`；模型对比时替换为目标对比模型名称 |
| `temperature/top_p/top_k` | 对比测试保持一致：0.6 / 0.6 / 20 |

响应记录规则：

1. `choices[0].message.content`：记录实际输出内容、字数和是否截断。
2. `choices[0].finish_reason`：`length` 表示达到 `max_tokens`，不能直接判定为模型故障；应提高上限后复测。
3. `usage.prompt_tokens`、`usage.completion_tokens`、`usage.total_tokens`：记录 token 消耗。
4. `prefill_time`：记录首轮输入处理耗时；`decode_time_arr`：记录逐 token 解码耗时，可计算平均解码耗时和吞吐。
5. HTTP 状态码、连接错误、空响应和 JSON 解析失败均记录为接口异常，并保留完整响应或日志。

## 7. 需要重点复测的风险项

1. 15750字文档的 AI 对话、文档对话、文档审核是否稳定超时，以及超时阈值和提示是否一致。
2. 文档差异分析在 4~6 账号并发时全部 timeout，而 3 账号并发可完成，应定位并发阈值、队列和资源瓶颈。
3. 0904 表中“总时长 01:45:00”与任务完成时刻间隔存在口径差异，应确认是 1分45秒还是 1小时45分。
4. 并发文档对话和审核中的“262/291、395/818、727/1346”等双值字段需要明确分别代表输入/输出还是问题数/依据数。
