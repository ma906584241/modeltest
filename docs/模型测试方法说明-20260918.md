# DeepSeek14B 模型测试方法说明

## 1. 测试目标

本测试用于验证 DeepSeek14B 在当前 MindIE 部署下的：

1. 接口连通性和请求参数是否生效。
2. AI 对话、长文本生成、代码生成和文档处理功能是否正常。
3. 不同 `max_tokens` 下的实际输出能力和上限。
4. 不同文档规模、并发数和压力轮次下的服务稳定性。
5. 响应耗时、输出吞吐、超时率、截断率和错误率。

测试脚本目录为 `automation`，输入文档位于 `modeltest` 根目录，测试说明位于 `docs`，测试结果保存在 `模型测评结果/<时间戳>/`。

## 2. 历史服务配置（运行前核对）

下表来自原测试环境，只作为结果解释基线。公开仓库不保存内部部署配置；实际执行应以 `automation/config.json` 和目标服务配置为准。

| 配置项 | 当前值 | 测试影响 |
|---|---:|---|
| 后端 | `mindieservice_llm_engine` | 使用 MindIE LLM 推理引擎 |
| 模型 | `deepseek14b` | 请求中的 `model` 必须与服务注册名称一致 |
| 模型实例数 | 1 | 所有请求进入同一个模型实例 |
| NPU | 0、1、2、3、4、5、6、7 | 8 卡推理，`worldSize=8` |
| `maxSeqLen` | 65536 | 输入和输出 token 总长度上限 |
| `maxInputTokenLen` | 32768 | 单次输入 token 上限 |
| `truncation` | `false` | 超过输入限制时不自动截断，应记录错误或失败 |
| `maxIterTimes` | 32768 | 单次生成迭代上限，容量测试最高测到 32768 tokens |
| `maxPrefillBatchSize` | 50 | Prefill 阶段最大批处理请求数 |
| `maxPrefillTokens` | 32768 | Prefill 阶段 token 调度上限 |
| `maxBatchSize` | 200 | Decode 阶段最大批处理请求数 |
| `cacheBlockSize` | 128 | KV Cache 分块大小 |
| `decodeTimeMsPerReq` | 50 | 调度吞吐估算参数，不等于实际单请求耗时 |

## 3. 统一请求参数

脚本默认使用 OpenAI 兼容接口：

```text
http://127.0.0.1:1025/v1/chat/completions
```

推理参数保持一致：

```json
{
  "model": "deepseek14b",
  "stream": false,
  "do_sample": true,
  "repetition_penalty": 1.0,
  "temperature": 0.6,
  "top_p": 0.6,
  "top_k": 20
}
```

非流式测试用于测量完整响应耗时和完整输出。流式测试需要增加 `--stream`，用于测量首事件、首正文和持续输出吞吐。

## 4. Linux 环境准备

进入仓库根目录：

```bash
cd /path/to/modeltest
```

确认 Python 版本：

```bash
python3 --version
```

要求 Python 3.9 或更高版本。脚本只使用 Python 标准库，不需要安装第三方依赖。

如接口需要鉴权：

```bash
export MODEL_API_KEY='实际密钥'
```

## 5. 测试执行顺序

### 5.1 接口连通性

先用短输出验证网络、端口、接口路径和模型名称：

```bash
python3 automation/run_tests.py \
  --mode smoke \
  --models deepseek14b \
  --max-tokens 32 \
  --timeout 300
```

判定标准：

- HTTP 状态为 200。
- 返回 `choices` 和 `usage`。
- 返回模型为 `deepseek14b`。
- `finish_reason` 为 `stop` 或 `length`。
- 有有效正文。

`max_tokens=32` 只用于连通性和短输出验证，不用于判断长文本能力。

### 5.2 功能测试

```bash
python3 automation/run_tests.py \
  --mode functional \
  --models deepseek14b \
  --max-tokens 4096 \
  --timeout 900
```

覆盖：

- AI 对话和旅游攻略生成。
- 0 到 1000、0 到 5000 连续序号输出。
- 重复文本输出。
- 长文写作和制度写作。
- JavaScript、Vue3、Python 代码生成。
- 英文诗歌翻译。
- 文档问答、摘要、大纲、审核和全文翻译。
- 文档差异分析。

功能测试必须同时检查机器指标和内容质量。接口成功不等于答案正确，文档问答、摘要、翻译、审核和代码结果需要人工抽样复核。

### 5.3 输出上限测试

```bash
python3 automation/run_tests.py \
  --mode capacity \
  --models deepseek14b
```

当前默认阶梯为：

```text
8192、16384、32768 tokens
```

每个档位默认重复 3 次。每次记录：

- 请求的 `max_tokens`。
- `completion_tokens`。
- `finish_reason`。
- 实际输出字符数。
- 总耗时和字符/秒。
- 是否 timeout。
- 是否出现服务错误。

结果解释：

- `OK`：请求正常结束。
- `EXPECTED_TRUNCATED`：该容量用例允许达到 token 上限，属于容量测量结果。
- `TRUNCATED`：非预期截断，需要提高上限复测。
- `TIMEOUT`：在请求总超时时间内没有完成。
- `ERROR`：接口、协议、返回模型或响应内容异常。

模型实际可用输出上限应取“连续多次稳定完成且不超时”的最高档位，而不是简单取服务配置中的 `maxIterTimes`。

### 5.3.1 全量输出测试

“全量输出测试”用于验证模型在允许的生成上限内是否能够持续输出完整内容，重点观察是否提前停止、达到 token 上限、超时或返回异常。它与普通功能测试不同：普通功能测试关注答案是否完成；全量输出测试主动要求模型尽可能持续生成。

#### 推荐提示词

使用主题明确、可持续扩展且不依赖外部资料的提示词：

```text
请围绕人工智能在企业知识管理中的应用，连续写作一篇结构完整的长文，包含背景、核心技术、系统架构、实施步骤、风险控制、案例分析和总结。请尽量持续输出直到自然结束，不要提前总结，不要询问我是否继续。
```

不要使用“写一篇万字长文”作为唯一判定条件，因为模型可能主动生成较短文章后自然结束，无法区分“自然完成”和“达到输出上限”。

#### 单档位全量输出

例如验证服务允许的最高生成档位：

```bash
python3 automation/run_tests.py \
  --mode functional \
  --models deepseek14b \
  --max-tokens 32768 \
  --timeout 1800
```

该命令会使用现有长输出和写作测试用例，最多允许生成 32768 tokens。报告中重点查看：

- `requested_max_tokens` 是否为 32768。
- `finish_reason` 是 `stop` 还是 `length`。
- `completion_tokens` 是否接近 32768。
- `total_s` 是否在超时时间内完成。
- `status` 是否为 `OK`、`TRUNCATED` 或 `TIMEOUT`。
- 输出文件是否存在明显截断、重复、空响应或内容失控。

#### 全量输出阶梯测试

推荐使用容量测试模式，逐级测量而不是只测最高值：

```bash
python3 automation/run_tests.py \
  --mode capacity \
  --models deepseek14b
```

默认阶梯为：

```text
8192 → 16384 → 32768 tokens
```

每个档位默认重复 3 次。判定建议如下：

| 结果 | 含义 |
|---|---|
| `stop` 且输出内容完整 | 模型在该档位自然结束，可继续测试更高档位 |
| `length` 且接近该档位上限 | 达到请求 token 上限，说明该档位不足以容纳完整输出，但不一定是模型故障 |
| `TIMEOUT` | 在规定时间内没有完成，应结合输入长度、并发和服务日志分析 |
| `ERROR` | 接口、协议、模型返回或服务异常 |

最终的“全量输出上限”应记录为：在固定提示词、固定采样参数、固定单请求条件和固定超时时间下，连续 3 次都能正常完成且内容完整的最高档位。若最高档位返回 `length`，只能说明请求上限被触达，不能证明模型只能生成这么多。

#### 流式全量输出

非流式请求只有在完整响应生成后才返回，无法准确测量首 token 和持续输出过程。需要观察实时输出时使用：

```bash
python3 automation/run_tests.py \
  --mode capacity \
  --models deepseek14b \
  --stream
```

流式测试应额外检查：

- 是否持续收到增量事件。
- 是否收到 `[DONE]` 结束标记。
- 首事件和首正文时间。
- 中途是否断流。
- 断流时是否保存已生成内容。
- 最终 `finish_reason` 是否可识别。

#### 全量输出的资源和时间估算

当前服务的 `decodeTimeMsPerReq=50` 只能作为调度配置参考，不能直接当作实际吞吐。32768 tokens 的单请求可能运行较长时间，建议：

1. 先执行 4096 和 8192 tokens。
2. 确认服务稳定后再执行 16384。
3. 最后执行 32768，并将单请求超时设置为 1800 秒或更高。
4. 全量输出期间不要同时运行压力测试，避免把容量限制和并发排队混在一起。

### 5.4 压力测试

```bash
python3 automation/run_tests.py \
  --mode stress \
  --models deepseek14b
```

当前压力测试使用 3 轮，扩展并发档位为：

```text
1、3、6、8、11、20
```

覆盖文档问答、摘要、审核和差异分析，并纳入不超过 16000 字符的文档。压力测试关注：

- 成功率和失败率。
- timeout 数量。
- P50、P95 和最大耗时。
- 批次墙钟时间。
- 成功请求吞吐。
- 并发升高后的性能下降。
- 是否出现整批失败或后续任务无法执行。

并发 20 是容量观察档位，不代表生产稳定容量。生产容量应在目标 SLA、目标成功率和持续运行时间下单独确认。

### 5.5 全量测试

```bash
python3 automation/run_tests.py \
  --mode all \
  --models deepseek14b
```

全量测试包含功能测试和压力测试，耗时较长，建议在服务器空闲时执行。

### 5.6 一次执行功能、压力和容量测试

如果需要把三类测试放在同一次运行中执行，使用新增的 `full` 模式：

```bash
python3 automation/run_tests.py \
  --mode full \
  --models deepseek14b
```

该模式会依次执行功能用例、压力并发批次和容量阶梯用例。运行结束后：

- 时间戳目录保存完整原始结果。
- `模型测评结果/<时间戳>/report.html` 保存本次详细报告。
- `模型测评结果/report.html` 更新为最近一次完整运行的固定汇总报告。

固定报告会被下一次 `full` 运行覆盖，历史结果仍保留在时间戳目录中。

## 6. 报告和原始证据

每次运行生成新的时间戳目录，不覆盖历史结果：

```text
模型测评结果/<时间戳>/report.html
```

报告中包含：

- 中文测试用例说明。
- 内部用例编号。
- 执行状态和自动检查结果。
- 首输出、首正文和总耗时。
- 输出字符数和字符吞吐。
- 错误或跳过原因。
- 本次运行配置。
- 逐请求结果和输出文件链接。

每个模型目录还保存：

```text
requests/*.request.json
requests/*.response.json
requests/*.result.json
requests/*.answer.txt
requests/*.raw.txt
requests/*.reasoning.txt
results.csv
results.json
stress_summary.json
```

## 7. 指标解释

| 指标 | 含义 |
|---|---|
| `prefill_time` | 服务端处理输入上下文的时间，单位以服务端实际定义为准 |
| `decode_time_arr` | 服务端逐 token 解码耗时数组，单位以服务端实际定义为准 |
| `completion_tokens` | 服务端统计的生成 token 数 |
| `total_s` | 客户端从建立请求到响应完成的总耗时 |
| `chars_per_second` | 正文字符数除以总耗时，不等于 token 吞吐 |
| P50/P95 | 同一压力批次正常完成请求的耗时分位数 |
| 成功率 | 正常完成请求数除以该批次实际请求数 |

非流式请求无法测量可靠的 TTFT。要评价用户实际感知的首响应速度，必须单独执行流式测试。

## 8. 结果判定建议

测试结论至少分为三层：

1. **接口层**：网络、HTTP、模型名、协议和响应结构是否正常。
2. **性能层**：耗时、吞吐、成功率、超时率和并发容量是否满足目标。
3. **质量层**：答案正确性、完整性、引用依据、翻译质量、代码可用性和差异识别准确率。

只有三层都满足验收标准，才能判定模型服务测试通过。`OK` 或 HTTP 200 只能证明请求完成，不能单独证明模型质量合格。

## 9. 当前限制

- `.doc` 二进制文件不能由当前标准库脚本直接解析，需要转换为同名 UTF-8 `.txt` 或 `.docx`。
- 文档摘要、翻译、审核和代码质量仍需要人工抽样，当前自动规则不代替专家评审。
- 当前测试记录模型 API 层，不包含完整 UI 上传、账号登录、检索链路和硬件利用率监控。
- timeout 归因应结合请求阶段、输入规模、服务日志和队列状态；本工具不采集 NPU 监控数据，因此不能仅凭测试报告判断硬件是否过载。
